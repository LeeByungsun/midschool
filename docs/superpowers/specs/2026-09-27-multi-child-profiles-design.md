# 다자녀 프로필 지원 설계

## 1. 목표

현재 하나의 학교·학년·반만 저장하는 Android 앱을 여러 자녀 프로필을 등록하고 전환할 수 있는 구조로 확장한다. 사용자는 홈 상단에서 현재 자녀를 바꾸며, 급식·시간표·학사 일정·가정통신문은 선택된 자녀의 학교 정보로 다시 조회된다.

자녀 이름 또는 별칭은 프로필 구분을 위해 필수로 입력받되 앱 전용 로컬 저장소에만 보관한다. Firebase Analytics, Crashlytics, 로그, NEIS API, 가정통신문 서버에는 자녀 이름과 프로필 ID를 전송하지 않는다.

## 2. 확정된 제품 결정

- 여러 자녀를 동시에 펼쳐 보이는 대시보드가 아니라 **현재 자녀 한 명을 전역 선택하는 방식**을 사용한다.
- 프로필 이름은 필수다. 실명 입력을 강제하지 않고 `민준`, `첫째`, `중학생` 같은 이름 또는 별칭을 허용한다.
- 프로필 이름은 앞뒤 공백을 제거한 1~10자로 제한한다.
- 공백 제거 후 같은 이름은 중복 등록하지 않는다. 선택 목록에서 자녀를 혼동하는 일을 방지하기 위한 제한이다.
- 자녀 수에는 임의의 제품 제한을 두지 않는다. 일반적인 1~5개 프로필에서 사용성을 검증한다.
- 프로필 순서 변경은 첫 버전 범위에서 제외하고 등록 순서를 유지한다.
- 프로필이 하나뿐일 때는 삭제할 수 없고 수정만 허용한다. 여러 개일 때 활성 프로필을 삭제하면 남아 있는 첫 프로필을 활성화한다.
- 타이머 설정과 실행 상태, Firebase 동의는 자녀별이 아니라 앱 전체 설정으로 유지한다.

## 3. 검토한 저장 방식

### 3.1 선택안: 전용 SharedPreferences의 단일 JSON 문서

`student_profiles.xml`에 버전, 활성 프로필 ID, 프로필 목록을 하나의 JSON으로 저장한다. 현재 앱이 이미 Gson과 SharedPreferences를 사용하고 있고 가족 단위 프로필 수가 작으므로 가장 단순하고 충분하다.

장점:

- 목록 추가·수정·삭제를 한 번의 저장으로 처리할 수 있다.
- 프로필별 동적 키를 관리하지 않아 고아 키가 생기지 않는다.
- 스키마 버전과 기존 단일 사용자 데이터 이전을 명시할 수 있다.
- 별도 DB 의존성과 마이그레이션 체계를 추가하지 않는다.

### 3.2 제외안: 프로필별 SharedPreferences 키

`child_1_name`, `child_2_school` 같은 구조는 삭제·재정렬·ID 변경 시 여러 키가 어긋날 수 있어 제외한다.

### 3.3 제외안: Room 데이터베이스

향후 출결 기록이나 사용자 작성 일정처럼 관계형 데이터가 추가되면 검토할 수 있지만, 현재는 작은 프로필 목록만 저장하므로 과도하다.

## 4. 도메인 모델과 저장 계약

기존 `StudentInfo`는 학교 조회에 필요한 값 객체로 유지하고, 이름과 안정적인 ID를 가진 `StudentProfile`이 이를 감싼다.

```kotlin
data class StudentProfile(
    val id: String,
    val displayName: String,
    val studentInfo: StudentInfo
)

data class StudentProfilesData(
    val schemaVersion: Int = 1,
    val activeProfileId: String,
    val profiles: List<StudentProfile>
)
```

- `id`: 앱이 생성한 UUID 문자열이다. 화면 표시, 네트워크 요청, Firebase 이벤트에는 넣지 않는다.
- `displayName`: 이름 또는 별칭이다. 로컬 화면에서만 사용한다.
- `studentInfo`: 기존 `schoolName`, `officeCode`, `schoolCode`, `schoolKind`, `grade`, `classroom`을 유지한다.
- `activeProfileId`: 현재 홈과 상세 화면에서 사용할 프로필을 가리킨다.
- `schemaVersion`: 이후 저장 형식 변경에 대비한다.

저장소 인터페이스는 일반 환경설정에서 프로필 책임을 분리한다.

```kotlin
interface StudentProfileRepository {
    val profiles: StateFlow<List<StudentProfile>>
    val activeProfile: StateFlow<StudentProfile?>

    fun getProfile(id: String): StudentProfile?
    fun addProfile(displayName: String, studentInfo: StudentInfo): Result<StudentProfile>
    fun updateProfile(profile: StudentProfile): Result<Unit>
    fun selectProfile(id: String): Result<Unit>
    fun deleteProfile(id: String): Result<Unit>
    fun requiresInitialSetup(): Boolean
}
```

`PreferencesRepository`는 타이머·동의·캐시·위젯 설정을 계속 담당하고, 기존 `getStudentInfo`, `saveStudentInfo`, `hasStudentInfo`는 프로필 전환 완료 후 제거한다. 새 저장소의 구현체는 프로세스 시작 시 JSON을 읽고 `StateFlow`를 초기화하며 모든 추가·수정·선택·삭제에서 JSON과 Flow를 함께 갱신한다.

잘못된 JSON이나 알 수 없는 스키마는 앱을 종료시키지 않는다. 읽기 실패 시 기존 단일 사용자 키를 복구 경로로 확인하고, 복구할 정보가 없으면 초기 설정으로 보낸다.

## 5. 기존 사용자 데이터 이전

업데이트 전 사용자의 학교 정보를 잃지 않도록 다음 순서로 한 번만 이전한다.

1. `student_profiles.xml`에 새 데이터가 있으면 이전을 수행하지 않는다.
2. 기존 `midschool_prefs.xml`의 학교·학년·반 값을 읽는다.
3. 값이 하나라도 있으면 UUID를 생성하고 이름이 비어 있는 이전용 프로필 초안을 만든다.
4. 스플래시 화면은 이름이 없는 이전용 프로필을 정상 프로필로 보지 않고 초기 설정 화면으로 보낸다.
5. 초기 설정 화면은 기존 학교·학년·반을 미리 채우고 자녀 이름 입력에 포커스를 둔다.
6. 사용자가 이름과 필수 항목을 확인해 저장하면 정상 프로필로 확정한다.
7. 새 JSON 저장이 성공한 뒤에만 기존 학교 관련 키를 삭제하고 이전 완료 표식을 남긴다.

기존 정보가 불완전해도 입력된 값은 초안에 보존한다. Firebase 동의가 이미 완료된 사용자는 자녀 이름 저장 후 동의 화면을 다시 보지 않고 홈으로 이동한다.

## 6. 조회 아키텍처와 데이터 흐름

현재 `SchoolRepositoryImpl`은 호출 시점마다 전역 `getStudentInfo()`를 읽는다. 이 방식은 자녀를 바꾸는 순간 진행 중이던 이전 자녀 요청이 새 화면에 도착할 수 있다. 새 구조에서는 조회에 사용할 `StudentInfo` 스냅샷을 모든 학교 데이터 호출에 명시적으로 전달한다.

```kotlin
suspend fun getMeals(student: StudentInfo, date: String?): Result<List<MealInfo>>
fun observeSchedules(student: StudentInfo, month: String?): Flow<Result<List<SchoolEvent>>>
fun observeTimetable(student: StudentInfo, date: String?): Flow<Result<List<TimetableItem>>>
suspend fun getNotices(student: StudentInfo, limit: Int): Result<NoticeFeed>
```

시간표 메서드는 `student.grade`와 `student.classroom`을 사용하므로 별도의 학년·반 인자를 제거한다. `searchSchools`만 자녀 문맥 없이 유지한다.

각 화면 ViewModel은 `activeProfile`을 관찰하고 `flatMapLatest` 또는 기존 작업 취소 후 재시작 방식으로 현재 프로필의 요청만 유지한다. 프로필 변경 순서는 다음과 같다.

1. 홈에서 프로필 선택
2. `StudentProfileRepository.selectProfile(id)`가 JSON과 `activeProfile`을 갱신
3. 홈 ViewModel이 이전 로드 작업을 취소하고 헤더를 즉시 변경
4. 선택된 프로필의 학교 정보 스냅샷으로 급식·일정·공지 재조회
5. 이전 프로필의 늦은 응답은 취소되거나 현재 상태에 반영되지 않음

기존 캐시 키는 이미 학교·학년·반·날짜를 포함하므로 자녀별로 안전하다. 동일 학교·학년·반을 사용하는 프로필은 같은 공공 데이터를 공유할 수 있어 프로필 ID를 캐시 키에 추가하지 않는다.

## 7. 화면과 상호작용

### 7.1 초기 설정

- 학교 선택 단계보다 앞에 `자녀 이름 또는 별칭` 입력을 추가한다.
- 입력 예시는 `민준`, `첫째`, `중학생`처럼 실명이 아니어도 된다는 점을 보여 준다.
- 기존 사용자의 이전 흐름에서는 학교·학년·반을 미리 채우고 이름만 비어 있게 한다.
- 첫 프로필 저장이 끝난 뒤 기존 Firebase 동의 흐름을 그대로 진행한다.

### 7.2 홈 프로필 전환

- 홈 히어로 상단에 현재 프로필 이름과 아래쪽 화살표가 있는 선택 칩을 배치한다.
- 학교 이름과 `2학년 3반` 정보는 현재 위계를 유지한다.
- 칩을 누르면 등록된 프로필을 단일 선택 목록으로 보여 준다.
- 각 행은 `민준`과 `한빛중학교 · 2학년 3반`을 표시한다.
- 목록 아래 `자녀 추가` 행동은 설정 화면의 빈 프로필 편집 상태로 이동한다.
- 설정 아이콘은 기존 위치와 48dp 터치 영역을 유지한다.
- TalkBack은 `현재 자녀 민준, 자녀 변경`으로 읽는다.

### 7.3 설정의 자녀 관리

별도 관리 앱 계층을 늘리지 않고 기존 `SettingsActivity` 상단의 학생 정보 영역을 자녀 관리 영역으로 확장한다.

- 현재 편집 중인 프로필 선택기
- `자녀 추가` 행동
- 이름 또는 별칭 입력
- 기존 학교 검색, 학년, 반 입력
- 여러 프로필일 때만 표시되는 `이 자녀 삭제` 행동
- 삭제 확인 대화상자

추가한 프로필은 저장 즉시 활성 프로필이 된다. 다른 프로필을 수정하면 활성 프로필 여부는 유지한다. 설정을 떠날 때 저장되지 않은 입력이 있으면 기존 초안 자동 저장 방식 대신 명시적 저장 또는 변경 폐기 확인을 사용해 다른 자녀에게 초안이 섞이지 않게 한다.

### 7.4 상세 화면

급식·시간표·학사 일정 화면은 상단에 현재 자녀 이름을 보조 문맥으로 표시한다. 홈에서 선택된 프로필을 사용하며 화면 복귀 또는 프로필 Flow 변경 시 데이터를 다시 불러온다. 상세 화면 안에는 별도 자녀 전환기를 추가하지 않아 한 화면에 하나의 전환 지점이라는 원칙을 유지한다.

## 8. 위젯

위젯은 전역 활성 프로필을 따라가게 하지 않고 **위젯별 프로필을 고정**한다. 그러면 사용자는 자녀별 위젯을 각각 홈 화면에 둘 수 있다.

```kotlin
data class WidgetSettings(
    val profileId: String,
    val showTomorrowTimetable: Boolean = true
)
```

- 위젯 설정 화면에 자녀 선택 목록을 추가한다.
- 기존 위젯은 `profileId`가 없으므로 첫 업데이트 때 현재 활성 프로필을 저장한다.
- 위젯이 가리키는 프로필이 삭제되면 현재 활성 프로필로 자동 대체하고 설정을 다시 저장한다.
- 위젯 로딩은 프로필의 `StudentInfo` 스냅샷을 `SchoolRepository`에 명시적으로 전달한다.
- 프로필 정보 수정·삭제 시 모든 위젯을 갱신한다. 단순 홈 프로필 전환은 프로필이 고정된 위젯 내용을 바꾸지 않는다.

## 9. 개인정보 및 Firebase 경계

자녀 이름과 UUID는 다음 경계를 지킨다.

- `student_profiles.xml`은 앱 전용 `MODE_PRIVATE`로 저장한다.
- `backup_rules.xml`과 `data_extraction_rules.xml`에서 해당 파일을 클라우드 백업과 기기 간 전송 모두 제외한다.
- Firebase Analytics 이벤트 매개변수, Crashlytics custom key·예외 메시지, 일반 로그에 이름과 UUID를 넣지 않는다.
- NEIS와 가정통신문 서버 요청에는 기존 학교·학년·반 조회값만 사용하고 이름과 UUID를 포함하지 않는다.
- 텔레메트리의 `schoolSaved`는 이전·현재 `StudentInfo`를 명시적으로 받아 학교 변경만 기록한다. 단순 프로필 전환을 `school_changed` 이벤트로 기록하지 않는다.
- 개인정보 처리방침에는 자녀 이름 또는 별칭이 단말 내부에서만 프로필 구분에 사용되고 서버로 전송되지 않는다고 명시한다.

학교 코드와 학교 종류는 사용자가 동의한 기존 Firebase 정책을 유지한다. 다자녀 기능이 새로운 외부 개인정보 전송을 만들지 않아야 한다.

## 10. 오류와 경계 조건

- 프로필 이름이 비어 있거나 10자를 초과하거나 기존 이름과 중복되면 저장하지 않고 입력 필드에 원인을 표시한다.
- 학교·학년·반이 완성되지 않으면 기존과 동일하게 설정 완료로 보지 않는다.
- 존재하지 않는 활성 ID는 첫 번째 유효 프로필로 복구하고 즉시 저장한다.
- 프로필 JSON 일부가 손상되면 유효한 프로필만 정규화해 복구하고, 하나도 없으면 초기 설정으로 이동한다.
- 마지막 프로필 삭제는 차단하고 `마지막 자녀는 삭제할 수 없어요. 정보를 수정해 주세요.`라고 안내한다.
- 프로필 전환 중 네트워크가 실패하면 해당 프로필의 동일 조회 키 캐시만 사용한다.
- 설정 화면에서 프로필을 바꾸기 전에 저장되지 않은 변경이 있으면 저장·버리기·취소 중 하나를 명시적으로 선택하게 한다.

## 11. 테스트 전략

### 저장 및 이전

- 프로필 목록 직렬화·역직렬화
- 추가·수정·선택·삭제와 활성 ID 유지
- 이름 공백·길이·중복 검증
- 마지막 프로필 삭제 차단
- 존재하지 않는 활성 ID 복구
- 손상 JSON 복구
- 기존 단일 학생 정보의 이름 입력 대기 이전
- 새 저장 성공 전 기존 키가 삭제되지 않는지 검증

### 조회와 화면 상태

- 프로필 전환 시 이전 요청 취소
- 늦게 완료된 이전 프로필 응답이 새 프로필 UI를 덮지 않음
- 같은 학교의 형제자매가 학교 공통 급식·일정 캐시를 공유함
- 다른 학년·반의 시간표 캐시가 섞이지 않음
- 초기 설정·홈·설정·상세 화면에 선택 프로필 문맥이 표시됨

### 위젯과 개인정보

- 위젯별 프로필 선택 저장
- 기존 위젯에 활성 프로필 자동 연결
- 삭제된 프로필의 위젯 fallback
- 자녀 이름과 UUID가 TelemetrySink 이벤트·문맥·예외에 들어가지 않음
- `student_profiles.xml`이 클라우드 백업과 기기 전송 규칙에서 제외됨

### 실제 단말 확인

- 자녀 두 명을 서로 다른 학교로 등록하고 홈 전환
- 같은 학교의 다른 학년·반으로 전환해 시간표 구분 확인
- 프로필 전환 후 급식·일정·공지·시간표 새로고침 확인
- 자녀별 위젯 두 개 배치 후 재부팅·자정 갱신 확인
- 시스템 글자 크기 1.0배와 1.3배에서 프로필 칩·목록·설정 입력 잘림 확인
- TalkBack으로 전환 칩과 삭제 확인 흐름 점검

## 12. 범위 제외

- 자녀 이름이나 설정의 계정·서버 동기화
- 보호자 로그인과 가족 공유
- 프로필 사진
- 자녀별 타이머 설정과 학습 기록
- 자녀 순서 변경
- Android 외 Web·iOS의 동시 구현

## 13. 완료 기준

- 기존 사용자의 학교·학년·반이 업데이트 과정에서 사라지지 않고 이름 입력 후 첫 프로필로 전환된다.
- 두 개 이상의 프로필을 추가·수정·선택·삭제할 수 있다.
- 홈과 모든 학교 데이터 화면은 활성 프로필의 정보만 표시한다.
- 진행 중 요청과 캐시로 인해 다른 프로필의 데이터가 섞이지 않는다.
- 위젯마다 특정 프로필을 선택해 유지할 수 있다.
- 자녀 이름과 UUID는 단말 밖으로 전송되거나 Android 백업에 포함되지 않는다.
- 관련 단위 테스트, QA 빌드, 린트와 실제 단말 다자녀 전환 시나리오가 통과한다.
